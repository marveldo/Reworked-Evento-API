# evento-api

The Evento backend in C++ with [Drogon](https://github.com/drogonframework/drogon): a port of
`Evento-backrnd` (Django), laid out like `cpp_server`. Same URLs and response shapes, so
`Evento-frontend` keeps working; photos now go straight from the browser to Cloudinary with a
signed upload (see
[Frontend changes](#frontend-changes)).

## Layout

```
bootstrap/     AppContext: settings, database, Redis task queue, email
controllers/   Auth, Users, Devices, Events, Photos, WebSockets (NotificationsSocketController)
middleware/    JwtMiddleware        authentication (Bearer token + device session check)
               DeviceInfoMiddleware User-Agent and client IP for login / Google sign-in
               RateLimitMiddlewares
services/      users, devices, events, notifications, realtime (Redis pub/sub), jwt,
               media (Cloudinary signed uploads), google, geo (ipinfo), email (Resend)
events/        EventBus + RegisterEvents: what happens in a request -> background tasks
queues/        TaskQueue (Redis lists) and the task handlers
input/         request parsing and validation
models/        generated by drogon_ctl from the database (don't edit)
migrations/    golang-migrate SQL files, from the Django models
templates/     welcome email, API docs page
```

## Run it locally

1. Postgres and Redis running; create a database called `evento`.
2. `cp .env.example .env` and fill it in.
3. Migrations: `scripts\migrate.bat` (or `migrate -path migrations -database "$DATABASE_URL" up`).
4. Models (only after changing migrations): `scripts\run.bat` / `scripts/gen_models.sh` fills
   `models/model.json` from `.env` and runs `drogon_ctl create model models`.
5. Build and run from the project root (it reads `.env`, `templates/` and `openapi.json` from there):
   ```
   cmake -S . -B build -G Ninja -DCMAKE_CXX_STANDARD=20
   cmake --build build --target evento_api
   ./build/evento_api
   ```
   or `scripts\dev.bat` to rebuild on every change. API docs: `GET /docs`.

Docker: `docker build -t evento-api .` then `docker run --env-file .env -p 10000:10000 evento-api`
(migrations run when the container starts). `render.yaml` sets it up on Render.

## Database (from the Django models)

| Django | table |
|---|---|
| `users.User` | `users` (+ `created_at`, `updated_at`) |
| `users.Notification` | `notifications` (+ `created_at`) |
| `users.DeviceInfo` | `device_info` (+ `created_at`) |
| `events.EventTag` | `event_tags` (`tag_name` unique) |
| `events.Event` | `events` (+ `updated_at`) |
| `Event.users` (M2M) | `event_users` (+ `registered_at`) |
| `Event.tags` (M2M) | `event_event_tags` |

Not carried over: Django's `groups` / `user_permissions` tables (admin internals) and SimpleJWT's
blacklist tables (a device session replaces them, see below).

## Endpoints

All under `/api/v1`, with the trailing slash, as in Django.

| | |
|---|---|
| `GET auth/` | check a token |
| `POST auth/register/` | `{full_name, email, password}` |
| `POST auth/login/` | `{email, password}` -> `access`, `refresh`, `data` (user + `device_id`) |
| `POST auth/refresh/` | `{refresh, device_id}` |
| `POST auth/google/` | `{access_token: <Google ID token>}` |
| `POST auth/logout/` | `{device_id, refresh_token}` |
| `GET auth/users/` | all users (now needs a login) |
| `GET / PUT / DELETE auth/current-user/` | the logged-in user |
| `GET auth/devices/` | your devices |
| `DELETE auth/logout-device/<id>/` | log a device out |
| `POST auth/socket-token/` | **new**: 60-second token for opening a WebSocket from the browser |
| `GET / POST events/` | `?tag=&limit=&offset=` / create |
| `GET events/<id>/` | one event |
| `GET / POST events/<id>/attendees/` | attendees / register `{email}` |
| `POST photos/signature/` | **new**: `{kind: profile|event}` -> signed Cloudinary upload |

WebSockets (not under `/api/v1`): `/ws/notifications/` and `/ws/home/`, authenticated with `?token=<socket token>`
(browsers) or `?access_token=<access>` (servers). The Origin header must be in `CORS_ALLOWED_ORIGINS`.
Close codes: `4401` device logged out, `4403` invalid or expired token, `1008` origin not allowed.

## What runs in the background now

Django did these inside the request; they're Redis tasks now (`events/RegisterEvents.cpp`,
`queues/handlers/TaskHandlers.cpp`):

| task | when |
|---|---|
| `create_notification` | someone registers for an event: saves the host's notification, then pushes it to their sockets |
| `send_logout` | a device is logged out: closes its sockets with 4401 |
| `send_email` | welcome email after sign-up / first Google sign-in |
| `update_user_location` | login: `"<country>,<city>"` from the IP (Django called geocoder.ip inside the login request) |
| `delete_photo` | a replaced profile picture is removed from Cloudinary |

## Frontend changes

Only the photos change. The file goes from the browser straight to Cloudinary; the API only signs
the upload, so the file never passes through this server.

1. Ask for a signature (with the user's access token):
   ```ts
   const { data } = await axinstance.post(`${process.env.BACKEND_URL}/photos/signature/`, { kind: 'profile' })  // or 'event'
   // data.data = { upload_url, public_id, kind, fields: { api_key, timestamp, signature, public_id, allowed_formats, transformation } }
   ```
2. Upload the file to Cloudinary from the browser:
   ```ts
   const form = new FormData()
   Object.entries(data.data.fields).forEach(([key, value]) => form.append(key, value as string))
   form.append('file', file)                         // jpg, png or webp
   await fetch(data.data.upload_url, { method: 'POST', body: form })
   ```
   Send the fields exactly as given: changing any of them breaks the signature.
3. Send the `public_id`:
   - settings page: `profile_img: data.data.public_id` to `PUT /auth/current-user/` (instead of the `profile_pic` file)
   - create event: `event_image: data.data.public_id` to `POST /events/` (instead of the file)

   The API checks the image exists in Cloudinary before saving it.

Responses still return full URLs in `profile_img` and `event_image`. Sending a file in
`profile_pic` / `event_image` now gets a 422 that points to the signature endpoint. Keep the
2 MB check in the frontend: Cloudinary caps the stored size (800 px profile pictures, 1600 px
event images) but a signed upload can't limit the file size.

## Behaviour differences from Django (on purpose)

- **Device sessions.** Tokens carry their `device_id`. As in Django, a token only works while it's
  the current access token of a device that still exists. Refresh tokens are single use: refreshing
  gives a new pair and the old refresh token stops working (SimpleJWT rotation + blacklist).
- **Google accounts** get a password that never matches, instead of the shared `SOCIAL_AUTH_PASSWORD`
  (which let anyone who knew it log into every Google account with email + password).
- **`events.created_by`** points at the user's id instead of storing their email, so changing an
  email doesn't detach their events. The API output (`hosted_by`) is the same.
- **Emails** are sent through Resend (as in `cpp_server`) instead of Gmail SMTP.
- **Passwords** are hashed with Argon2. Django `pbkdf2_sha256` hashes still work if you copy users
  over, and are upgraded on the next login.
- **Validation errors** use the same `{"errors": [{field, message}]}` shape and 422 status; some
  message texts differ.
- **Rate limits** (as in `cpp_server`): login per email, sign-up, refresh, upload signatures, and 120
  requests a minute per user.
